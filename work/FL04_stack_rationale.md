# Assignment: Three Roads: Choose Your Stack with AI (FL-04)

## 1. Core Portfolio Operational Constraints

To evaluate architecture options objectively, the system pressure-tests candidates against four non-negotiable operational boundaries:
- **Financial Baseline:** $0.00 (Strictly Free Tools and Hosting Tiers Only).
- **Honest Engineering Competency Level:** High-utility beginner focused on data workflows rather than deep JavaScript production web frameworks.
- **Functional Requirements (Sitemap & Content Map):** A multi-page technical portfolio structure presenting data contracts, unsupervised evaluation tables, and a clear call-to-action intake path.
- **Display Requirements:** High-density long-form technical reading, embedded live data analysis figures, and native links to public code repositories.
- **Dynamic Infrastructure State:** Not yet required. The initial deployment operates perfectly as a statically compiled interface.

## 3. The Structural Front-Runner Pressure-Test

- **What breaks if I pick the simplest (Road 1)?** The ability to easily format code repositories, clean text tables, and markdown structures decays, making the site look like a generic marketing page rather than a rigorous research manuscript.
- **What do I maintain if I pick the most powerful (Road 3)?** Continuous pipeline dependency errors, local package management updates, and production build container crashes that waste valuable analytical time.
- **Can I maintain and finish this in time?** Yes, by prioritizing Road 2. It fits perfectly into a two-week timeline, avoiding build systems while preserving custom codebase architecture.
- **Does it show my work how it needs to be shown?** Yes. It lets long-form text blocks, data matrices, and repository links stand as the loudest, cleanest elements on the screen.

---

## 4. Definitive Architectural Selection Rationale

### Chosen Stack: 
Plain Code (HTML5 / Minimalist CSS Stylesheets) hosted natively via GitHub Pages.

### Rejected Alternatives & Justification:
1. **Carrd / No-Code (Road 1):** Rejected. While fast to spin up, it severely restricts custom layout designs, meaning data contract visualization metrics would be compromised by rigid template boxes.
2. **Next.js Framework (Road 3):** Rejected. Building a highly complex JavaScript app to render static text blocks and data charts introduces massive maintenance overhead that does not serve our core research goal.

### Long-Term Maintenance Assessment:
I can easily maintain, update, and defend this choice to an academic or technical committee. Because the architecture relies on plain code, it will never break due to outdated external packages, it remains free forever, and it links directly to our master code branch, acting as instant proof of deployment capability.
